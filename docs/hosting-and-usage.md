# Hosting and using generated CSS and WOFF2 slices

This guide explains how to deploy and use the `@font-face` stylesheet (`<slug>.css`) and `.woff2` slice files generated by `cleome build`, `slice_font`, or `slice_fonts`.


## 1. Output layout and URL resolution

Running `cleome build` writes a stylesheet and a slice directory under `--out-dir` (`dist` by default). Each `.woff2` filename includes an 8-character SHA-256 content hash by default (`--no-filename-hash` disables the hash):

```text
dist/web/
├── source-han-sans-jp.css
└── slices/
    ├── source-han-sans-jp-kanji-rare-01-4c91e0a2.woff2
    ├── ...
    ├── source-han-sans-jp-kanji-freq-01-9b120f84.woff2
    ├── source-han-sans-jp-symbols-ext-01-7d3e11c0.woff2
    ├── source-han-sans-jp-symbols-ui-1f8a92d3.woff2
    ├── source-han-sans-jp-kana-core-3a7f91bc.woff2
    └── source-han-sans-jp-latin-8f02e1a4.woff2
```

Inside `<slug>.css`, each `@font-face` rule points to `./slices/<filename>.woff2` by default:

```css
/* [kana-core] Tier 1: Core Kana, CJK Punctuation & Fullwidth ASCII (380 glyphs, 28.4 KB) */
@font-face {
  font-family: 'Source Han Sans JP';
  font-style: normal;
  font-weight: 250 900;
  font-display: swap;
  src: url('./slices/source-han-sans-jp-kana-core-3a7f91bc.woff2') format('woff2');
  unicode-range: U+3000-303F, U+3041-3096, U+3099-30FF, U+31F0-31FF, U+FF01-FF60, U+FFE0-FFE6;
}
```

When bundling multiple static font files (`cleome build Regular.ttf Bold.ttf -o dist/web`), Cleome inserts a variant token into each slice filename so all variants share one `slices/` directory without collisions:

* **Multiple weights (`400`, `700`).** `<slug>-400-<slice_id>-<hash8>.woff2`, `<slug>-700-<slice_id>-<hash8>.woff2`
* **Multiple widths and weights (`75%`, `100%`).** `<slug>-w75-400-<slice_id>-<hash8>.woff2`, `<slug>-w100-400-<slice_id>-<hash8>.woff2`
* **Multiple styles (`normal`, `italic`).** `<slug>-400-<slice_id>-<hash8>.woff2`, `<slug>-400-italic-<slice_id>-<hash8>.woff2`


### Choose `--slices-dir` and `--url-prefix`

In CSS, `url('./slices/...')` resolves relative to the URL of the `.css` file, not the HTML document. Match the flags to how your site serves stylesheets:

* **Static `public/` directory (Next.js, Astro, Vite, or a static CDN directory).**
  Keep the default relative URLs and write directly into the static folder:

  ```bash
  cleome build SourceHanSansJP-VF.otf -o public/fonts/source-han-sans-jp
  ```

  Link `/fonts/source-han-sans-jp/source-han-sans-jp.css` from HTML. The browser resolves `./slices/*.woff2` to `/fonts/source-han-sans-jp/slices/*.woff2`.

* **CSS imported into a bundler or inlined into `<style>`.**
  When a bundler merges `<slug>.css` into `/assets/index-<hash>.css` or inlines it into HTML, relative `./slices/...` paths either get rewritten by the bundler (copying 90+ `.woff2` files into the build graph) or resolve against the document URL. Place the slices in your static `public/` directory or on a CDN, set `--url-prefix` to an absolute path or URL, and pass `--css-out` to write the stylesheet directly into `src/`:

  ```bash
  # Next.js / Astro: write slices to public/fonts/slices/ and CSS to src/styles/fonts.css
  cleome build SourceHanSansJP-VF.otf \
    -o public/fonts \
    --url-prefix "/fonts/slices" \
    --css-out src/styles/fonts.css

  # Full CDN origin URL prefix
  cleome build SourceHanSansJP-VF.otf \
    -o dist/cdn-upload \
    --url-prefix "https://cdn.example.com/fonts/source-han-sans-jp/slices"
  ```

* **Bundler-managed asset directory (`src/assets/`).**
  When placing both `<slug>.css` and `.woff2` slices inside a bundler-managed directory where Vite or Webpack adds its own content hash, pass `--no-filename-hash`:

  ```bash
  cleome build SourceHanSansJP-VF.otf -o src/assets/fonts --no-filename-hash
  ```

* **Flat directory (CSS and `.woff2` files in the same folder).**
  Pass `--slices-dir .` to write `.woff2` files into `--out-dir` with `url('./<slug>-<slice_id>-<hash8>.woff2')`:

  ```bash
  cleome build SourceHanSansJP-VF.otf -o dist/flat --slices-dir .
  ```

## 2. Load and style fonts in HTML and CSS

Place font `<link>` tags in `<head>` after `<meta charset="utf-8">`, viewport `<meta>` tags, `<title>`, and any synchronous inline `<script>` or `<script type="importmap">`, and before external `<script>` tags:

```html
<!doctype html>
<html lang="ja">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Page Title</title>

  <!-- Synchronous inline <script> (such as theme setup) and <script type="importmap"> go BEFORE stylesheets -->

  <!-- Only when serving slices from a separate CDN origin: preconnect with crossorigin -->
  <link rel="preconnect" href="https://cdn.example.com" crossorigin>

  <!-- Optional: preload at most the Tier 1 core slices (printed by `cleome build`), always with crossorigin -->
  <link rel="preload" href="/fonts/source-han-sans-jp/slices/source-han-sans-jp-kana-core-3a7f91bc.woff2" as="font" type="font/woff2" crossorigin>

  <!-- Generated @font-face stylesheet and application CSS -->
  <link rel="stylesheet" href="/fonts/source-han-sans-jp/source-han-sans-jp.css">
  <link rel="stylesheet" href="/assets/main.css">

  <!-- External scripts (defer or type="module") go AFTER stylesheets -->
  <script type="module" src="/assets/app.js"></script>
</head>
```

Reference the `font-family` name in your CSS rules:

```css
body {
  font-family: "Source Han Sans JP", sans-serif;
  font-weight: 400;
}

h1 {
  font-weight: 750;
  font-stretch: 85%; /* Supported when the input font has a `wdth` axis */
}
```

To inspect the `font-family`, `font-weight`, `font-stretch`, and `font-style` descriptors Cleome emits for a font without writing files, run:

```bash
cleome plan SourceHanSansJP-VF.otf
```


### Variable font axes and static font bundles

* **Variable fonts (`fvar`).** A variable font shares one set of `.woff2` slices across all weights and widths (`font-weight: 250 900`, `font-stretch: 70% 100%`), and across `@font-face` style rules (`normal`, `italic`, `oblique <min>deg <max>deg`) when the font has `ital` or `slnt` axes. Using `font-weight: 400` in body text and `font-weight: 700` in headings downloads each required slice once.
* **Static font bundles.** Passing multiple static `.ttf` or `.otf` files (`cleome build Regular.ttf Bold.ttf -o dist/web`) emits a separate set of `@font-face` rules and `.woff2` slice files per variant. Bundle only the static weights used on the page so headings and body text do not download unused weight files. See [`docs/architecture-and-rationale.md`](architecture-and-rationale.md) for how Cleome extracts axis descriptors and per-variant slices.


### OpenType layout features and UVS/IVS sequences

See [`docs/architecture-and-rationale.md`](architecture-and-rationale.md) for the full rationale behind Tier 1 co-location, `GSUB` and `GPOS` lookup retention, and `cmap` Format 14 variation sequences, and [`skills/cleome/SKILL.md`](../skills/cleome/SKILL.md) for `--layout-features` (`SliceConfig.layout_features`) configuration.

* **What works in CSS.** Single-glyph OpenType features (`vert`, `vrt2`, `palt`, `vpal`, `halt`, `vhal`, `fwid`, `pwid`, `jp78`, `jp83`, `jp90`, `nlck`, `ruby`) and `cmap` Format 14 variation sequences (`IVS` `U+E0100..U+E01EF` and `VS1..VS16`) work in every slice. Multi-glyph lookups (`ccmp`, `mark`, `mkmk`, `chws`, `vchw`, `kern`, `liga`, `ljmo`, `vjmo`, `tjmo`) work within each Tier 1 core slice (`latin`, `kana-core`, `hangul-core`, `cjk-core`).
* **Cross-slice limit.** Browsers do not apply `GSUB` or `GPOS` lookups across separate `@font-face` slice files, so multi-glyph lookups whose input glyphs belong to different slices (such as pair kerning between `latin` and `kana-core`, or a `U+0300-036F` combining mark applied to a symbol in `symbols-ext`) are not shaped across slice boundaries.

## 3. Preloading and placement mistakes to avoid

When adding `<slug>.css` and `.woff2` slices to HTML, avoid these patterns:

* **Do not preload all `.woff2` slices or Tier 2-4 Kanji, Hanzi, or Hangul chunks.** `unicode-range` partitioning lets the browser download only the slices needed by the characters on the page (3 to 12 slices out of 90+ on typical pages). Preloading unused Tier 2-4 slices wastes bandwidth and competes with page scripts and images. To remove the CSS-to-font request waterfall for above-the-fold text, preload at most the Tier 1 core slices for your primary language (`<slug>-latin.woff2`, `<slug>-kana-core.woff2`, `<slug>-hangul-core.woff2`, or `<slug>-cjk-core.woff2`).
* **Do not omit `crossorigin` on `<link rel="preload" as="font">` or `<link rel="preconnect">`.** Include `crossorigin` even when the `.woff2` files are hosted on the same origin. Under the W3C CSS Fonts and Fetch specifications, `@font-face` requests always use anonymous CORS mode. Omitting `crossorigin` makes the browser fetch the slice twice or open a non-CORS connection that font requests cannot reuse.
* **Do not load `<slug>.css` via CSS `@import`.** Browser preload scanners cannot see `@import url('./source-han-sans-jp.css');` inside another external stylesheet, which delays fetching `<slug>.css` until the parent stylesheet downloads and parses. Use a `<link rel="stylesheet">` tag in `<head>` or bundle the CSS at build time.
* **Do not put blocking `<script src="...">` before `<link rel="preconnect">` or `<link rel="stylesheet">`, and do not put synchronous inline `<script>` or `<script type="importmap">` after `<link rel="stylesheet">`.** A synchronous inline `<script>` after `<link rel="stylesheet">` blocks the HTML parser until the stylesheet finishes downloading. A blocking external `<script src="...">` before `<link rel="preconnect">` stops WebKit's preload scanner from opening the early connection while the parser is blocked.
* **Do not place `<link rel="stylesheet" href=".../<slug>.css">` inside `<body>`.** An external stylesheet in `<body>` blocks the HTML parser in Chromium and causes flashes of unstyled text. Place `<link rel="stylesheet">` inside `<head>`.

## 4. HTTP headers (CORS, compression, and caching)

### Cross-origin resource sharing (`Access-Control-Allow-Origin`)

When serving `.woff2` slices from a separate CDN domain or subdomain (such as `cdn.example.com` while the document is on `www.example.com`), the CDN must return an `Access-Control-Allow-Origin` header on `.woff2` responses:

```http
Access-Control-Allow-Origin: *
Content-Type: font/woff2
```

Without `Access-Control-Allow-Origin`, browsers reject cross-origin `@font-face` responses per [W3C CSS Fonts Module Level 4, section 4.9](https://www.w3.org/TR/css-fonts-4/#font-fetching-requirements).


### Compression (`Content-Encoding`)

* **`.woff2` slice files (`Content-Type: font/woff2`).** WOFF2 binaries already compress table streams with Brotli. Do not re-compress `.woff2` responses with HTTP `Content-Encoding: gzip` or `br`.
* **`<slug>.css` (`Content-Type: text/css; charset=utf-8`).** Compress `.css` responses with HTTP Brotli (`br`) or `gzip`. Cleome's 1-token Tier 4 cascade ranges compress a single-variant CJK stylesheet to 6.0-7.5 KB over Brotli.


### Cache invalidation and content hashes (`Cache-Control`)

When content hashes are enabled (the default; see section 1 and [`skills/cleome/SKILL.md`](../skills/cleome/SKILL.md) for `SliceConfig.filename_hash`), Cleome removes superseded `<slug>(-<variant>)-<slice_id>-[0-9a-f]{8}.woff2` files on rebuild:

1. **Serve `.woff2` slices with immutable caching**:

   ```http
   Cache-Control: public, max-age=31536000, immutable
   ```

2. **When updating the font or slicing configuration**, re-run `cleome build` into the same directory. Unchanged slices (such as `latin` or `kana-core`) keep their filename and stay cached in browsers and CDN edge nodes, while slices whose `.woff2` bytes changed get a new `<hash8>` filename in `<slug>.css`.

3. **When using `--no-filename-hash`**, include a version segment in your hosting directory path (such as `/fonts/source-han-sans-jp/v1/` to `/v2/`) whenever you set `Cache-Control: public, max-age=31536000, immutable` so `<slug>.css` and all `.woff2` slices rotate together.
