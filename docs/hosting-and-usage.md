# Hosting and Using Generated CSS and WOFF2 Slices

This guide explains how to deploy and use the `@font-face` stylesheet (`<slug>.css`) and `.woff2` slice files generated by `cleome build` (or `slice_font` / `slice_fonts`).


## 1. Output Layout and URL Resolution

Running `cleome build` writes a stylesheet and a slice directory under `--out-dir` (`dist` by default):

```text
dist/web/
├── source-han-sans-jp.css
└── slices/
    ├── source-han-sans-jp-kanji-rare-01.woff2
    ├── ...
    ├── source-han-sans-jp-kanji-freq-01.woff2
    ├── source-han-sans-jp-symbols-ext-01.woff2
    ├── source-han-sans-jp-symbols-ui.woff2
    ├── source-han-sans-jp-kana-core.woff2
    └── source-han-sans-jp-latin.woff2
```

Inside `<slug>.css`, each `@font-face` rule points to `./slices/<filename>.woff2` by default:

```css
/* [kana-core] Tier 1: Core Kana, CJK Punctuation & Fullwidth ASCII (380 glyphs, 28.4 KB) */
@font-face {
  font-family: 'Source Han Sans JP';
  font-style: normal;
  font-weight: 250 900;
  font-display: swap;
  src: url('./slices/source-han-sans-jp-kana-core.woff2') format('woff2');
  unicode-range: U+3000-303F, U+3041-3096, U+3099-30FF, U+31F0-31FF, U+FF01-FF60, U+FFE0-FFE6;
}
```

When bundling multiple static font files (`cleome build Regular.ttf Bold.ttf -o dist/web`), Cleome inserts a variant token into each slice filename so all variants share a single `slices/` directory without collisions:

* **Multiple weights (`400`, `700`)**: `<slug>-400-<slice_id>.woff2`, `<slug>-700-<slice_id>.woff2`
* **Multiple widths and weights (`75%`, `100%`)**: `<slug>-w75-400-<slice_id>.woff2`, `<slug>-w100-400-<slice_id>.woff2`
* **Multiple styles (`normal`, `italic`)**: `<slug>-400-<slice_id>.woff2`, `<slug>-400-italic-<slice_id>.woff2`


### Choosing `--slices-dir` and `--url-prefix`

In CSS, `url('./slices/...')` resolves relative to the URL of the `.css` file itself (not the HTML document). Choose the flag combination that matches how your site serves stylesheets:

* **Static `public/` directory (Next.js `public/`, Astro `public/`, Vite `public/`, or static CDN directory)**:
  Keep the default relative URLs and output directly into your static folder:

  ```bash
  cleome build SourceHanSansJP-VF.otf -o public/fonts/source-han-sans-jp
  ```

  Link `/fonts/source-han-sans-jp/source-han-sans-jp.css` from HTML. The browser resolves `./slices/*.woff2` to `/fonts/source-han-sans-jp/slices/*.woff2`.

* **CSS imported into a bundler or inlined into `<style>`**:
  If a bundler merges `<slug>.css` into `/assets/index-<hash>.css` or inlines it into HTML, relative `./slices/...` paths will either be rewritten by the bundler (duplicating 90+ `.woff2` files into the build graph) or resolve against the document path. Place the slices in your static `public/` directory (or on a CDN) and set `--url-prefix` to an absolute path or URL:

  ```bash
  # Root-relative URL prefix for static public/fonts/slices/
  cleome build SourceHanSansJP-VF.otf \
    -o public/fonts \
    --url-prefix "/fonts/slices"

  # Full CDN origin URL prefix
  cleome build SourceHanSansJP-VF.otf \
    -o dist/cdn-upload \
    --url-prefix "https://cdn.example.com/fonts/source-han-sans-jp/v1/slices"
  ```

* **Flat directory (CSS and `.woff2` files in the same folder)**:
  Pass `--slices-dir .` to write `.woff2` files directly into `--out-dir` with `url('./<slug>-<slice_id>.woff2')`:

  ```bash
  cleome build SourceHanSansJP-VF.otf -o dist/flat --slices-dir .
  ```

## 2. Loading and Styling in HTML and CSS

Link the generated stylesheet in `<head>` and reference the `font-family` name in your CSS rules:

```html
<link rel="stylesheet" href="/fonts/source-han-sans-jp/source-han-sans-jp.css">
```

```css
body {
  font-family: "Source Han Sans JP", sans-serif;
  font-weight: 400;
}

h1 {
  font-weight: 750;
  font-stretch: 85%; /* Supported when the input font has a `wdth` axis */
}
```

To inspect the exact `font-family`, `font-weight`, `font-stretch`, and `font-style` descriptors Cleome will emit for a font before building, run:

```bash
cleome plan SourceHanSansJP-VF.otf
```


### Variable Font Axes vs. Static Font Bundles

* **Variable fonts (`fvar`)**: Cleome extracts continuous descriptor ranges (`font-weight: 250 900`, `font-stretch: 70% 100%`) from `fvar`. All weights and widths share the same set of `.woff2` slices, so using `font-weight: 400` in body text and `font-weight: 700` in headings downloads each required slice only once. When a variable font includes an `ital` or `slnt` axis, Cleome emits `@font-face` rules for each supported style (`normal`, `italic`, `oblique <min>deg <max>deg`) pointing to the same `.woff2` slice files.
* **Static font bundles**: When you pass multiple static `.ttf`/`.otf` files (`cleome build Regular.ttf Bold.ttf -o dist/web`), Cleome emits a separate set of `@font-face` rules and `.woff2` slice files per variant. Keep the number of bundled static weights to those actually used on the page so headings and body text do not download redundant weight variants.


### OpenType Layout Features and UVS/IVS Sequences

Cleome retains all OpenType layout features (`layout_features=('*',)` with forward `GSUB` glyph closure) and `cmap` Format 14 variation sequences by default:

* **Single-glyph substitutions work in every slice**: Vertical writing alternates (`vert`, `vrt2`), proportional and halfwidth metrics (`palt`, `vpal`, `halt`, `vhal`, `fwid`, `pwid`), JIS glyph set variants (`jp78`, `jp83`, `jp90`, `nlck`), and `ruby` glyphs are preserved in every `.woff2` slice.
* **Intra-slice multi-glyph lookups (`ccmp`, `mark`, `mkmk`, `chws`, `vchw`, `kern`, `liga`, `ljmo`, `vjmo`, `tjmo`)**: Browsers do not apply `GSUB` or `GPOS` lookups across separate `@font-face` slice files. Cleome co-locates base characters with their combining marks and paired punctuation in Tier 1 so intra-slice shaping works out of the box:
  * **`latin` (all locales)**: ASCII/Latin base letters and Combining Diacritical Marks (`U+0300-036F`, `U+1AB0-1AFF`, `U+1DC0-1DFF`, `U+FE20-FE2F`).
  * **`kana-core` (`jp`)**: Hiragana, Katakana, combining voiced marks (`U+3099-309A`), CJK punctuation (`U+3000-303F`: `「」`, `『』`, `【】`, `、`, `。`), and fullwidth forms (`U+FF01-FF60`), preserving `chws`/`vchw` contextual spacing between consecutive brackets and punctuation.
  * **`hangul-core` (`kr`)**: CJK punctuation (`《》`, `「」`), Hangul Compatibility Jamo (`U+3130-318F`), and Conjoining Hangul Jamo (`U+1100-11FF`, `U+A960-A97F`, `U+D7B0-D7FF`).
  * **`cjk-core` (`sc`, `tc`, `hk`)**: CJK punctuation (`〈〉`, `『』`, `「」`, `《》`), Bopomofo (`U+3100-312F`, `U+31A0-31BF`), and Mandarin tone marks (`U+02C7`, `U+02C9-02CB`, `U+02D9`), preserving `GPOS` `mark`/`mkmk` tone attachment and `chws`/`vchw` bracket spacing.
* **Cross-slice limitation**: Multi-glyph lookups whose input glyphs belong to different slices (for example, pair kerning between a Latin character in `latin` and a Kana character in `kana-core`, or a `U+0300-036F` combining mark applied to a symbol in `symbols-ext`) are pruned by `fontTools.subset` and cannot shape across `@font-face` boundaries.
* **Ideographic Variation Sequences (`cmap` Format 14)**: Standard IVS (`U+E0100..U+E01EF`) and Standardized Variants (`VS1..VS16`, `U+FE00..U+FE0F`) are retained inside the slice containing their base character without leaking standalone selector code points into the Format 4/12 base `cmap`.

## 3. Preloading and `unicode-range` Behavior

Do **not** add `<link rel="preload" as="font">` tags for all `.woff2` slices. `unicode-range` partitioning is designed so the browser downloads only the slices required by the characters rendered on the current page (typically 3 to 12 slices out of 90+). Preloading unused Tier 3 or Tier 4 slices wastes bandwidth and contends with critical page resources.

If you want to eliminate the CSS-to-font request waterfall for above-the-fold text, preload at most the Tier 1 core slice(s) for your primary language (`<slug>-latin.woff2` and/or `<slug>-kana-core.woff2`, `<slug>-hangul-core.woff2`, or `<slug>-cjk-core.woff2`):

```html
<link rel="preload" href="/fonts/source-han-sans-jp/slices/source-han-sans-jp-kana-core.woff2" as="font" type="font/woff2" crossorigin>
<link rel="stylesheet" href="/fonts/source-han-sans-jp/source-han-sans-jp.css">
```

Always include the `crossorigin` attribute on `<link rel="preload" as="font">`, even when the `.woff2` files are hosted on the same origin. Under the W3C CSS Fonts and Fetch specifications, `@font-face` requests always use anonymous CORS mode; omitting `crossorigin` on the preload causes the browser to fetch the slice twice.

## 4. HTTP Headers (CORS, Compression, and Caching)

### Cross-Origin Resource Sharing (`Access-Control-Allow-Origin`)

When serving `.woff2` slices from a separate CDN domain or subdomain (such as `cdn.example.com` while the document is on `www.example.com`), the CDN must return an `Access-Control-Allow-Origin` header on `.woff2` responses:

```http
Access-Control-Allow-Origin: *
Content-Type: font/woff2
```

Without `Access-Control-Allow-Origin`, browsers reject cross-origin `@font-face` responses per [W3C CSS Fonts Module Level 4, section 4.9](https://www.w3.org/TR/css-fonts-4/#font-fetching-requirements).


### Compression (`Content-Encoding`)

* **`.woff2` slice files (`Content-Type: font/woff2`)**: WOFF2 binaries are already Brotli-compressed at the table stream level. Do not re-compress `.woff2` responses with HTTP `Content-Encoding: gzip` or `br`.
* **`<slug>.css` (`Content-Type: text/css; charset=utf-8`)**: Enable HTTP Brotli (`br`) or `gzip` compression on `.css` responses. Cleome's 1-token Tier 4 cascade ranges compress a single-variant CJK stylesheet to ~6.0-7.5 KB over Brotli.


### Cache Invalidation and Versioned Paths (`Cache-Control`)

Cleome generates deterministic, human-readable slice filenames (`<slug>-<slice_id>.woff2`) rather than embedding content hashes in filenames. If you update the upstream font file, change `SliceConfig` parameters, or upgrade Cleome, regenerating into the same path overwrites `<slug>.css` and `<slug>-*.woff2` in place.

If a browser or CDN caches an old `<slug>-kanji-freq-01.woff2` while serving a newly generated `<slug>.css` (or vice versa), code points that moved between slices can fail to match the cached `.woff2` binary. To cache `.woff2` slices with `immutable` safely:

1. **Include a version segment in your hosting directory path** (for example, `/fonts/source-han-sans-jp/v1/`):

   ```bash
   cleome build SourceHanSansJP-VF.otf -o public/fonts/source-han-sans-jp/v1
   ```

2. **Serve `.woff2` slices under that versioned path with long-lived immutable caching**:

   ```http
   Cache-Control: public, max-age=31536000, immutable
   ```

3. **When updating the font or slicing config**, deploy to a new versioned directory (`/fonts/source-han-sans-jp/v2/`) and update the `<link rel="stylesheet">` URL so `<slug>.css` and all `.woff2` slices switch atomically.
